# Position-wise loss — does this model use its context?

Model `artifacts/hf-tt-tnt-v1`, tokens `artifacts/tokens-stratified/val_ids.npy`, window length 512, 256 windows per bucket (batch size 32), generated by `scripts/probe_context_use.py`.

Checkpoint step 10,787 (tt-tnt-v1's final checkpoint). Tokens: artifacts/tokens-stratified/val_ids.npy (stratified per-source validation split).

*(Everything through the "Position-wise loss (all sources combined)" table below is written by `scripts/probe_context_use.py` and will be overwritten verbatim by re-running it. The "Reproducing the original finding" and "Per-source validation" sections after the table are hand-authored against this specific run and are not regenerated automatically -- matching `docs/measurements/per-source-loss-tt-tnt-v1.md`'s own convention -- so re-append/update them by hand after a future re-run.)*

## Why this exists

If a model's per-token loss keeps falling as position (context length) increases, it is using the context it has. If the loss goes flat, the model has stopped benefiting from additional tokens of context -- raising the context window further would not help it. This is the tool version of the probe that first found `artifacts/hf-tt-tnt-v1`'s loss goes flat at position ~64 (`.superpowers/max-context-investigation.md` §7), now reproducible with standard errors instead of a bare mean.

## Method, in brief

- Windows are sampled uniformly at random (with replacement) from the token array, the same way `scripts/eval_per_source.py::sample_windows` does.
- Cross-entropy is computed directly against `logits`, never through the `labels=` kwarg (which shifts a second time -- see `eval_per_source.py`'s docstring).
- Each bucket reports **mean ± standard error over independent windows** -- first averaged across positions within a window, then across windows, so within-window autocorrelation is not mistaken for independent samples. `n` is the number of windows the estimate rests on, never the number of tokens.

## Reproducing the original finding

`.superpowers/max-context-investigation.md` §7 ran a one-off, uncommitted probe on this same
model and found per-token loss goes flat at position ~64 and stays flat (or gets fractionally
worse) out to 511, on both `gutenberg_children` (a book source) and `tinystories` (a short-item
source). That was the single most decisive measurement this project had made, and it is the
reason this tool exists. **It reproduces.**

The all-sources-combined table above already shows the shape: a steep drop from `[0,32)`
(4.1112) to `[64,128)` (3.1958), then a near-flat tail -- `[128,256)` 3.0941, `[256,512)`
3.0834, a gap of only 0.0107 nats against a bucket SEM of ~0.065, an order of magnitude below
noise. That alone is consistent with the original finding, but a blended average over nine
sources of very different difficulty could in principle hide a source that is still improving
-- exactly the risk `--blend-manifest`'s per-source breakdown exists to catch (see below for
why that flag could not be exercised live in this session).

## Per-source validation (why this run used exact spans instead of `--blend-manifest`)

`artifacts/corpus/*` was being concurrently rebuilt by another agent (into
`artifacts/tokens-v3`) while this tool was built and validated, so `--blend-manifest`'s live
path -- which re-tokenizes `--blend` (`artifacts/corpus/blend.txt`) -- was deliberately never
exercised against the real corpus in this session, to avoid reading a file mid-rewrite. That
code path (`stratified_source_spans`, `verify_stratified_reconstruction`,
`tokenize_blend_by_source`) is exercised instead by `tests/test_probe_context_use.py` against
synthetic corpora, and should be re-run for real against `docs/measurements/blend_manifest.json`
once the concurrent rebuild is done and settled.

In the meantime, a per-source check against `--tokens artifacts/tokens-stratified/val_ids.npy`
was still possible without touching `artifacts/corpus/`: `artifacts/tokens/train_ids.npy` (the
**flat**, non-stratified split `tt-tnt-v1` was actually trained on) concatenates all nine
sources in sorted-name order with no gaps, and
`docs/measurements/per-source-loss-tt-tnt-v1.md`'s own `train_tokens` column gives each
source's exact length in that concatenation -- the nine values sum to exactly
`len(train_ids)` (353,495,970) and the running total after `wikipedia_simple` matches its own
reported `train_tokens` (17,731,721) exactly, so the implied per-source boundaries are exact,
not estimated. Content at the midpoint of every one of the nine implied ranges was decoded and
manually confirmed to match its expected source (e.g. `procedural`'s midpoint is a pumpkin-pie
recipe; `tinystories`'s is "kids... you can have some more fruit"). Three sources were then
probed via `scripts/probe_context_use.py` on a token sub-range safely inside (not touching) each
one's boundary:

| source | span probed (train_ids offsets) | [0,32) | [32,64) | [64,128) | [128,256) | [256,512) |
|---|---|---:|---:|---:|---:|---:|
| gutenberg_children | [40,000,000, 85,000,000) | 4.0237 ± 0.0364 | 3.6301 ± 0.0399 | 3.6118 ± 0.0318 | 3.5629 ± 0.0273 | 3.5134 ± 0.0242 |
| tinystories | [210,000,000, 305,000,000) | 2.3678 ± 0.0374 | 1.8524 ± 0.0349 | 1.7254 ± 0.0262 | 1.7298 ± 0.0228 | 1.7195 ± 0.0217 |
| spine | [150,000,000, 188,000,000) | 4.3121 ± 0.0402 | 3.8922 ± 0.0375 | 3.8246 ± 0.0372 | 3.7256 ± 0.0330 | 3.7560 ± 0.0275 |

(256 windows per bucket, same seed/batch-size as the aggregate run above; command:
`scripts/probe_context_use.py --hf-model artifacts/hf-tt-tnt-v1 --tokens <extracted span
.npy> --seq-len 512 --n-windows 256`.)

**This reproduces the original finding directly, source by source:**

- **`gutenberg_children` (a book source)**: falls sharply through position 64 (4.02 -> 3.61),
  then goes nearly flat -- 3.61 -> 3.56 -> 3.51, a further drop of only 0.10 nats across the
  remaining 3/4 of the window. The tail value (3.51) is within 0.07 nats of
  `per-source-loss-tt-tnt-v1.md`'s train-sample figure for this source (**3.5836**) and within
  0.12 of `max-context-investigation.md`'s own tail reading (**3.6317**) -- consistent given a
  different, smaller sub-span and a different sample of windows within it.
- **`tinystories` (a short-item source)**: falls through position 64 (2.37 -> 1.85 -> 1.73),
  then is **completely flat** from 64 to 512 -- 1.7254, 1.7298, 1.7195, a spread of 0.01 nats
  against a SEM of ~0.02-0.03, i.e. no detectable improvement at all past position 64. This
  matches `max-context-investigation.md`'s own tinystories reading almost exactly (its
  `[64,128)`/`[384,511)` pair was 1.7436/1.7467, also flat to within noise) and is within 0.10
  of `per-source-loss-tt-tnt-v1.md`'s **1.8214**.
- **`spine`** (not in the original two-source table, added here as a third, independent check):
  same shape -- 4.31 -> 3.89 -> 3.82 -> 3.73 -> 3.76, i.e. flat and fractionally *worse* from
  `[128,256)` to `[256,512)`, the same "plateaus, then ticks up slightly" pattern the original
  investigation reported for `gutenberg_children`. Tail value 3.7560 is within 0.08 of
  `per-source-loss-tt-tnt-v1.md`'s **3.8357**.

**Conclusion: the tool reproduces the original ~64-token plateau finding**, on the same two
sources the original ad-hoc probe used and on a third source it did not, with absolute values
consistent (within a few hundredths of a nat, well inside the noise expected from sampling a
different sub-span) with both `max-context-investigation.md` §7 and
`per-source-loss-tt-tnt-v1.md`. Neither the original probe nor this tool is shown to be wrong;
the finding stands.
