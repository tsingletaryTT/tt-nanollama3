# Packaging and Publishing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish NanoLlama3's weights to the Hugging Face Hub and package it as a tt-kernel v4 bundle that serves through the Tenstorrent vLLM plugin.

**Architecture:** Four stages — repair the HF artifact, publish it to `episod/`, establish whether the plugin's existing Llama adapter can serve a model this small, then author the v4 manifest and serve. The third stage is the real risk and is deliberately its own task.

**Tech Stack:** `huggingface_hub` 0.36.2 / `hf` CLI, tt-kernel (v4 schema), the Tenstorrent vLLM plugin, pytest

- `HF_TOKEN` set in the environment (37 chars, no stored token file — it is env-based).

- **Namespace decision: `episod/`.**

## The constraint that dictates ordering — and a correction

An earlier note in this project said the model card and license must exist **before** the first `tt-kernel push`. **That is wrong**, and the correction matters because it inverts the sequence.

`hub.tag_repo` (`src/tt_kernel/hub.py:56-66`) does:

```python
card = ModelCard.load(repo_id)                    # prose body IS preserved
existing = list(getattr(card.data, "tags", None) or [])
card.data = ModelCardData(tags=sorted(set(existing) | set(tags)))   # all other front matter destroyed
card.push_to_hub(repo_id, repo_type="model")
```

So tags merge and the prose survives, but **`license`, `pipeline_tag`, `library_name`, `datasets`, and `base_model` are wiped from front matter** every time it runs. It runs on every push (`cli.py:288`, `cli.py:503`), and `set_catalog_listing` (`cli.py:1470`, `:1484`) does the same on publish/unpublish.

**Consequences:**

1. Putting the license in card front matter *before* pushing does not protect it.
2. Use the **repo-level license setting** (via `HfApi`/`create_repo`), which is independent of card front matter and which `tag_repo` cannot touch.
3. **Verify front matter after every tt-kernel operation**, and restore what was lost.

This is also a genuine tt-kernel defect worth reporting upstream: `tag_repo` silently destroys licensing metadata on a repo whose card it did not author.

## Global Constraints

- SPDX header pair on new files; Python 3.10+.
- **No bare `assert` for guards** in production code.
- `pyproject.toml` must NOT be modified.
- **Never write under `artifacts/checkpoints/`.** `artifacts/hf/` may be regenerated by `scripts/convert_checkpoint.py`.
- **If a step produces a number or a state that decides pass/fail, it must be a test**, not a shell command in prose.
- **Nothing is published without the user's explicit go-ahead.** Creating a public repo and uploading weights are outward-facing and irreversible in practice. Task 2 stops for confirmation before its first push.
- The model is a **demonstration**: ~22M params, 49,152,000 tokens ≈ 0.43 of one epoch, TinyStories (synthetic, simple). Every public description must say so.

## Task 1: Repair the HF artifact

**Files:**
- Modify: `convert/to_hf.py`
- Test: `tests/test_to_hf.py`

**Interfaces:**
- Produces: `artifacts/hf/generation_config.json`; corrected `tokenizer_config.json`; an assertion tying `max_position_embeddings` to the checkpoint header.

Three defects, all found during review and all cheap now, expensive after publication.

- [ ] **Step 1: Write failing tests**

```python
def test_generation_config_is_written(tmp_path):
    """A published model needs eos_token_id and default sampling recorded."""
    # convert into tmp_path, then:
    gen = json.loads((out / "generation_config.json").read_text())
    assert gen["eos_token_id"] == 2
    assert gen["bos_token_id"] == 1
    assert gen["pad_token_id"] == 3


def test_tokenizer_class_matches_what_actually_loads(tmp_path):
    """tokenizer_config.json declared PreTrainedTokenizer; it loads as ...Fast."""
    cfg = json.loads((out / "tokenizer_config.json").read_text())
    assert cfg["tokenizer_class"] == "PreTrainedTokenizerFast"


def test_max_position_embeddings_equals_the_trained_sequence_length(tmp_path):
    """Guards the serving trap: tokenizer_config advertises model_max_length
    1000000000000000019884624838656. Deriving max_model_len from the tokenizer
    yields a stack accepting 4k contexts from a model trained to 256."""
    cfg = json.loads((out / "config.json").read_text())
    header = peek(CKPT)
    assert cfg["max_position_embeddings"] == header["seq_len"] == 256
```

- [ ] **Step 2: Implement** — emit `generation_config.json`, correct `tokenizer_class` when copying the tokenizer, add the `max_position_embeddings` guard to `convert_checkpoint`.

- [ ] **Step 3: Decide the duplicate-embedding question and record it**

`model.safetensors` is **68.6 MB** for a 44 MB model, because `lm_head.weight` duplicates `embed_tokens.weight` under weight tying. Conventional practice with `tie_word_embeddings: true` is to omit `lm_head.weight`.

**Do not change this silently.** Verify first that `AutoModelForCausalLM.from_pretrained` still loads and ties correctly with `lm_head.weight` absent, and that the parity gate still passes. If either fails, keep the duplicate and record why. Report the measured size difference either way.

- [ ] **Step 4: Regenerate `artifacts/hf/`, confirm the full suite passes, commit**

The parity gate (`tests/test_numpy_parity.py`) must still pass — it is the check that the artifact is still numerically correct after edits.

## Task 2: Publish weights to `episod/` on the Hub

**Files:**
- Create: `scripts/publish_to_hub.py`
- Create: `docs/model-card.md` (the card body, version-controlled here so it can be restored after tt-kernel wipes front matter)

**Interfaces:** produces a populated HF model repo. No new Python API.

**This task performs an irreversible public action. Stop and ask before the first upload.**

- [ ] **Step 1: Write the model card**

`docs/model-card.md` is the source of truth, kept in the repo so it can be re-applied after any tt-kernel operation. It must state:

- **What it is:** a ~22M-parameter Llama-3-style model trained from scratch on Tenstorrent Blackhole with `ttml`, as a demonstration of an end-to-end TT-native pipeline.
- **Honest capability framing:** 49,152,000 tokens ≈ **0.43 of one epoch** over its training split, on TinyStories — a synthetic corpus of simple children's stories with a small vocabulary and deliberately regular grammar. Low loss there is unsurprising. **It is not a capable general model.**
- **Measured numbers:** first train loss 10.6875 (≈ `ln(32000) = 10.37`), final 1.9219, held-out validation 1.8781; 3000 steps in 6 min 47 s on a single Blackhole chip at ~0.134 s/step (`mesh_shape [1, 1]`; the dev host is a QuietBox 2 with four chips, but training uses one).
- **Corpus and licence:** TinyStories (`roneneldan/TinyStories`) is **CDLA-Sharing-1.0**, a share-alike data licence. Whether weights trained on CDLA-Sharing data are a "Data Derivative" is unsettled; we do not assert they are not. State this plainly.
- **Known limitation:** all 13 RMSNorm gammas are frozen at exactly 1.0 — bf16 parameters at 1.0 have a ulp of 0.0039 while Adam updates were ~3.6e-4, and `stochastic_rounding` was off. The model trained with its norm layers effectively frozen. Link the remedies.
- **Verification:** the conversion is validated against an independently-derived NumPy reimplementation of ttml's forward pass, agreeing to ~1e-5 on logits.
- **Links** to this repo and to `docs/model-development-troubleshooting.md`.
- **Sample output**, presented as one sample rather than proof.

- [ ] **Step 2: Create the repo with the licence set at repo level**

```python
from huggingface_hub import HfApi
api = HfApi()
api.create_repo("episod/tt-nanollama3", repo_type="model", private=True, exist_ok=True)
```

**Create it private.** It is flipped public in Step 5, after everything is verified — an irreversible public artifact should not be the first thing that exists.

Set the licence via the API rather than card front matter, since `tag_repo` cannot reach the repo-level setting.

- [ ] **Step 3: Ask the user before uploading**

Report what will be uploaded — file list and total size — and **wait for explicit confirmation**. Do not proceed on inference.

- [ ] **Step 4: Upload and verify by round-trip**

Upload `artifacts/hf/` and the card. Then verify from the Hub, not from local state:

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
m = AutoModelForCausalLM.from_pretrained("episod/tt-nanollama3")
```

Assert the config fields survived the round trip — particularly `max_position_embeddings == 256` and `tie_word_embeddings is True`.

- [ ] **Step 5: The repo stays PRIVATE. Do not flip it public in this task.**

Amended by the user after the plan was written: **the repo is not made public until the model
is verified running on Tenstorrent hardware through the vLLM plugin** — not merely loading via
`transformers` on the host.

The reason is sound: a Hub round-trip proves the artifact is well-formed, but this project's
whole thesis is that well-formed and correct are different things. A model that loads on the
host and cannot serve on the hardware it was trained on would be a poor thing to have made
public. Publishing is effectively irreversible — people clone, caches propagate, links get
shared — so the gate belongs after the strongest evidence, not the earliest.

Flipping public becomes **Task 4 Step 5**, after `tt-kernel serve` answers a real query.

## Task 3: Establish whether the existing plugin adapter can serve this model

**Files:**
- Create: `docs/adapter-viability.md`

**Interfaces:** none — produces a written finding that determines Task 4's shape.

**This is the plan's real risk, which is why it is its own task before any manifest is written.**

The plugin registers `TTLlamaForCausalLM` → `models.tt_transformers.tt.generator_vllm:LlamaForCausalLM` (`vllm_tt_plugin/platform.py:229,245`). Our model is standard HF Llama, so **no custom adapter may be needed** — a significant simplification over this project's original design, which assumed a bespoke `TTNanoLlama3`.

But `tt_transformers` targets production Llamas (8B, 70B). Our model is `hidden_size=384`, `num_hidden_layers=6`, `num_attention_heads=6`, `num_key_value_heads=3`, `head_dim=64`, `max_position_embeddings=256`, `vocab_size=32000`.

- [ ] **Step 1: Determine, from source, whether that adapter accepts this configuration**

Read `models/tt_transformers/` in the tt-metal tree. Look specifically for: minimum dimension or layer-count assumptions; tile-alignment requirements on `hidden_size`, `head_dim`, or `vocab_size`; hardcoded model-family detection (name-based config lookup is common and would reject an unknown model); mesh/device-count assumptions; and any minimum `max_position_embeddings`.

Record findings with file:line citations, and state plainly whether the answer is yes, no, or undetermined.

- [ ] **Step 2: If it looks viable, prove it minimally**

Attempt to instantiate the adapter against the published repo with the smallest possible harness — do not build the full serving stack to answer a compatibility question.

- [ ] **Step 3: If it is not viable, scope the alternative**

Options, in increasing cost: pad the config to whatever the adapter requires (only if that does not change the model); write a minimal `TTNanoLlama3` adapter; or serve via a different path and record that v4 packaging is blocked on adapter support.

**A finding of "not viable" is a successful outcome for this task.** Do not force a manifest that cannot serve.

## Task 4: Author the v4 manifest, push, and serve

**Files:**
- Create: `bundle/manifest.json`
- Test: `tests/test_manifest.py`

Shape confirmed against `tt_kernel/manifest.py`:

```json
{
  "schema_version": "4",
  "name": "tt-nanollama3",
  "arch": "blackhole",
  "device_count": 1,
  "platform":   { "ttnn": ">=0.73" },
  "runtime":    { "kind": "vllm", "version": ">=0.24" },
  "mesh":       { "devices": 1, "topology": "1x1" },
  "entrypoint": { "class": "<from Task 3>", "arch_name": "<from Task 3>" },
  "resources":  { "max_model_len": 256, "max_num_seqs": 8 },
  "weights":    { "repo": "episod/tt-nanollama3" }
}
```

- [ ] **Step 1: Test the manifest before pushing anything**

`max_model_len` **must** be 256. Assert it equals the model's `max_position_embeddings`, and add a comment naming the trap: `tokenizer_config.json` advertises `model_max_length: 1000000000000000019884624838656`, so deriving it from the tokenizer produces a server accepting 4k contexts from a 256-context model — degraded output, no error.

Also assert `weights.repo` matches the published repo id, since tt-kernel never validates that the weights repo matches `entrypoint.arch_name`.

- [ ] **Step 2: `tt-kernel push`, then immediately check what it did to the card**

After pushing, re-read the repo's card and record which front-matter fields survived. Restore the licence and any other lost fields from `docs/model-card.md`. **This is the step the ordering correction exists for.**

- [ ] **Step 3: Pull and serve**

`tt-kernel pull` onto a clean bundles dir, then `tt-kernel serve`, then query the endpoint. Report the actual response.

- [ ] **Step 5: Flip the HF repo public — the final gate**

Only now, and only if all of these hold:

- `tt-kernel pull` + `tt-kernel serve` brought up an endpoint on Tenstorrent hardware
- a real query returned coherent output (report it verbatim)
- the model card's front matter has been restored after `tag_repo` damaged it
- the repo-level licence is still set

**Ask the user before flipping.** Report the serving output first; publishing is their call, not
a step to take on inference.

If serving does not work — including if Task 3 found the adapter unviable — **the repo stays
private** and that is a correct outcome. A private repo with verified weights is more useful
than a public one that cannot serve.

- [ ] **Step 6: Record results in CLAUDE.md**

Including what `tt-kernel push` did to the model card, since that is the finding most useful to the next person.

## Known risks

- **The frozen-gamma limitation is real and must be disclosed**, not omitted because it is unflattering.
